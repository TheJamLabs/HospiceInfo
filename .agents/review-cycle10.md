## Findings

### F-1 [risk-accepted] — Discovery rows hit by transient DDG transport errors (incl. rate limits across the 190 rounds) have no non-terminal outcome value

The ADR-0045 vocabulary is 8 values with only `discovery-found` non-terminal. If a discovery round returns 429/5xx/timeout from `html.duckduckgo.com` (plausible over 190 sequential rounds), the script must **not** write a terminal `not-found` row for that site — that row would be silently unretryable until a human deletes it (manual refresh). The code must distinguish a definitive empty result (→ `not-found`) from a transport error (→ row left unwritten; the run is incomplete). This is self-enforcing as designed: the G2 gate requires the log to cover every in-scope row exactly once, so an incomplete log fails certification and the resume logic re-attempts the un-written rows on re-invoke; exit 0 is reserved for completed data outcomes. No architecture change needed — this is a coding requirement to carry into QA (verify a simulated 429 leaves the row un-logged, and that re-running re-attempts it).

### F-2 [risk-accepted] — Geocode-tier coverage gaps (Nominatim no-match) leave committed entries out of `shops.json`

New crawl entries whose postcode/address no-match Nominatim (and the 12 existing address-only rows) are committed to `shops-website.json` yet dropped at build L1063 (`shopGeoMissing`, not a failure). They are logged individually (geocoder "no match" line; crawl-log note), satisfying "missing entries are logged individually". The built-count floor (item 5 below) is against the **pre-crawl** built count, and the geocoder's L37 skip guarantees the 138 existing keys are never re-fetched or changed, so the committed-138 contribution to the built count is invariant. Outcome-based acceptance per owner policy — never blocks.

### F-3 [risk-accepted] — Playwright binary availability is an environment risk, not a build/test dependency

The binary lives in the user cache, never in the repo; the script never downloads it (prints `npx playwright install chromium`, affected pages fall through to `blocked`/`unreadable` per ADR-0044). No test in the 5-test plan touches the network or the binary (all pure/file-shape), so `npm test` and the build chain never require it. If the binary is absent at crawl time, QA records the affected slice as risk-accepted, documented — the acceptance gate (committed entries + complete log) remains reachable without it.

### F-4 [risk-accepted] — Crawl log size

Bounded: exactly one row per in-scope row (190 discovery + 18 confirm = 208), rewritten per run, not appended across runs → tens of KB total, stable per site. No mitigation needed; recorded for completeness.

### F-5 [risk-accepted] — External-endpoint drift (DDG `uddg` format, site title/h1 heuristics)

Discovery depends on an unversioned public HTML endpoint and per-site heuristics. Drift degrades to per-row `not-found`/`no-website` entries (audited, human-recoverable via delete-row + re-run, ADR-0045 — "manual refresh"), and the conservative own-domain acceptance rule (name tokens in the second-level domain + full name in root title/h1) bounds false positives. Matches the repo's existing tolerance for external data sources (Nominatim, OSM). Never blocks.

### F-6 [risk-accepted] — `trinityhospice.co.uk`-class WAF intermittency (403→200)

Research §6 lead verification shows plain `fetch` gets 403 intermittently. The architecture's Component C engagement order (plain fetch → headless render → PDF text → `unreadable`, with `blocked` only after the headless tier also fails) is the correct absorption: intermittent 403s are resolved by the headless attempt, persistent blocks are logged `blocked` with the site left to human audit. Per-site `browser.newContext()` (ADR-0044) prevents cookie/store bleed between sites. Covered as written; no change required.
